MVP de Engenharia de Dados

Data Warehouse para Análise Proteômica e Genômica de eIF4E em Plantas

Contexto Acadêmico

Este projeto constitui o MVP (Minimum Viable Product) desenvolvido como requisito avaliativo da disciplina de Engenharia de Dados (código 40530010057_20250_02), integrante do curso de Especialização em Data Science and Analytics da Pontifícia Universidade Católica do Rio de Janeiro (PUC-Rio).

Objetivo do MVP

O objetivo principal deste MVP é demonstrar a implementação completa de uma arquitetura de Data Warehouse aplicada a um domínio científico real, integrando conceitos fundamentais de engenharia de dados com necessidades práticas da bioinformática e genômica vegetal.

Justificativa Técnica e Científica

A escolha de proteínas eIF4E de plantas como caso de uso se justifica por múltiplos fatores:

  • Relevância Biológica: eIF4E é um fator essencial para tradução proteica e desempenha papel crucial na resistência viral em plantas cultivadas
  • Complexidade de Dados: Integra múltiplas dimensões de informação (sequências, taxonomia, funções, estruturas, variantes)
  • Dados Heterogêneos: Requer tratamento de dados estruturados (metadados) e semi-estruturados (sequências, anotações)
  • Volume Adequado: Aproximadamente 1.247 proteínas de 450 espécies, permitindo análises estatísticas significativas sem exigir infraestrutura de Big Data
  • Aplicabilidade Prática: Resultados podem ser utilizados em melhoramento genético e desenvolvimento de cultivares resistentes a vírus

Decisões Arquiteturais

1. Escolha do SGBD: SQLite

Justificativa:

  • Zero Configuration: Não requer instalação ou configuração de servidor, ideal para portabilidade e reprodutibilidade
  • Performance Adequada: Para datasets de até 100.000 registros, SQLite oferece performance comparável a SGBDs cliente-servidor
  • ACID Compliant: Garante transações atômicas, consistentes, isoladas e duráveis
  • Cross-Platform: Banco de dados portável em arquivo único, facilitando distribuição e versionamento
  • Adequado ao MVP: Simplicidade operacional permite foco em modelagem e ETL, não em administração de infraestrutura

2. Modelo Dimensional: Star Schema

Justificativa:

  • Otimização para Análise: Queries analíticas (agregações, GROUP BY) são mais eficientes com JOINs simples de 1 nível
  • Facilidade de Entendimento: Estrutura intuitiva espelhando conceitos de negócio (dimensões = "quem, o quê, onde, quando")
  • Performance de Queries: Reduz número de JOINs necessários comparado a snowflake schema
  • Escalabilidade: Permite adicionar novas dimensões sem reestruturar tabelas fato existentes

3. Pipeline ETL em Python

Justificativa:

  • Ecossistema Científico: Bibliotecas especializadas (BioPython, pandas) para manipulação de dados biológicos
  • Integração de APIs: Biblioteca requests facilita consumo de APIs REST de forma robusta
  • Manipulação de Dados: Pandas oferece estruturas de dados eficientes para transformações complexas
  • Reprodutibilidade: Código versionado permite reprodução exata do pipeline em diferentes ambientes

Componentes Detalhados do Sistema

1. Camada de Dados (Data Warehouse)

Modelo Dimensional

Implementa Star Schema com as seguintes tabelas:

Tabelas Dimensão (Descritores):
  • dim_organism: Informações taxonômicas (espécie, família, ordem, classe, reino, linhagem completa)
  • dim_gene: Informações gênicas (nome do gene, sinônimos, tipo)
  • dim_function: Anotações Gene Ontology (GO ID, termo, aspecto, categoria)
  • dim_location: Localização subcelular (compartimento, topologia, evidência)
Tabelas Fato (Métricas e Observações):
  • fact_protein: Dados centrais de proteínas (UniProt ID, sequência, peso molecular, pI, versão)
  • fact_variant: Variantes e mutações (posição, resíduo original/variante, significância clínica, associação com doenças)
  • fact_domain: Domínios proteicos (nome, tipo, posições inicial/final, InterPro ID)
Tabelas Associativas (Many-to-Many):
  • protein_function: Relaciona proteínas com múltiplas funções GO
  • protein_location: Relaciona proteínas com múltiplas localizações celulares

Integridade e Constraints

  • Primary Keys em todas as tabelas (IDs auto-incremento)
  • Foreign Keys com ON DELETE CASCADE para manter integridade referencial
  • UNIQUE constraints em campos de negócio (uniprot_id, go_id)
  • NOT NULL em campos obrigatórios
  • CHECK constraints para validação de domínios

Índices para Performance

  • Índices em chaves estrangeiras para otimizar JOINs
  • Índices compostos em campos frequentemente filtrados (organism_id, gene_id)
  • Índice em uniprot_id para buscas diretas por ID

2. Pipeline ETL (Extract, Transform, Load)

Extract (Extração)

Fonte de Dados: UniProtKB REST API

  • Endpoint: https://rest.uniprot.org/uniprotkb/search
  • Query: Filtro por termo "eIF4E" AND taxonomia "Viridiplantae" (plantas)
  • Campos Extraídos: accession, protein_name, gene_names, organism, taxonomy, sequence, go_annotations, subcellular_location, domains
  • Formato: JSON estruturado
  • Paginação: Cursor-based pagination para coletar todos os resultados (500 registros por página)
  • Rate Limiting: Intervalo de 1 segundo entre requisições para respeitar políticas do servidor
  • Error Handling: Retry logic com backoff exponencial para falhas transitórias de rede

Transform (Transformação)

Processamento de Dados:

A. Normalização de Sequências
  • Remoção de espaços e caracteres inválidos
  • Conversão para uppercase
  • Validação de aminoácidos válidos (20 aminoácidos padrão)
  • Cálculo de comprimento de sequência
B. Parsing Taxonômico
  • Extração de espécie, nome comum, taxonomy ID
  • Parsing de linhagem completa (split por delimitador ";")
  • Identificação de níveis hierárquicos (reino, filo, classe, ordem, família, gênero)
  • Tratamento de linhagens incompletas ou inconsistentes
C. Processamento de Gene Ontology
  • Extração de termos GO (ID, nome, aspecto, código de evidência)
  • Classificação por aspecto (F: função molecular, P: processo biológico, C: componente celular)
  • Deduplicação de termos GO idênticos
D. Cálculo de Propriedades Físico-Químicas
  • Peso molecular (soma de massas atômicas dos resíduos)
  • Ponto isoelétrico (cálculo baseado em pKa de grupos ionizáveis)
  • Índice de instabilidade
  • Índice alifático
E. Validação e Limpeza
  • Verificação de campos obrigatórios
  • Validação de tipos de dados
  • Tratamento de valores nulos ou missing
  • Deduplicação de registros

Load (Carga)

Processo de Carga no Data Warehouse:

Etapas de Carga:
  1. Carga de Dimensões (Ordem Importante):
    • dim_organism (sem dependências)
    • dim_gene (sem dependências)
    • dim_function (sem dependências)
    • dim_location (sem dependências)
  2. Resolução de Foreign Keys: Após inserir dimensões, buscar IDs gerados para estabelecer relações
  3. Carga de Tabelas Fato:
    • fact_protein (referencia dim_organism e dim_gene)
    • fact_variant (referencia fact_protein)
    • fact_domain (referencia fact_protein)
  4. Carga de Associações Many-to-Many:
    • protein_function (referencia fact_protein e dim_function)
    • protein_location (referencia fact_protein e dim_location)
Controle Transacional:
  • BEGIN TRANSACTION no início do processo
  • COMMIT apenas após sucesso completo de todas as etapas
  • ROLLBACK em caso de erro em qualquer etapa (atomicidade)
  • Logging detalhado de cada operação para auditoria e debugging

Execução e Monitoramento

  • Trigger Manual: Comando python etl.py no diretório data_warehouse
  • Tempo de Execução: Aproximadamente 30-45 segundos para dataset completo
  • Logs: Arquivo de log com timestamp, nível (INFO/WARNING/ERROR) e detalhes de cada operação
  • Métricas Coletadas: Registros extraídos, transformados, carregados, tempo por etapa, erros encontrados

Exportação de Dados

Conceitos de Engenharia de Dados Aplicados

Mapeamento entre teoria e prática demonstrada no projeto

1. Modelagem de Data Warehouse

  • Star Schema: Modelo dimensional com tabela fato central (fact_protein) conectada a 4 dimensões (organism, gene, function, location)
  • Granularidade: Nível de proteína individual permite análises detalhadas sem agregação prematura
  • Slowly Changing Dimensions: Dimensão organism implementa Type 1 (overwrite), adequado para correções taxonômicas
  • Tabelas Fato Múltiplas: fact_variant e fact_domain complementam fact_protein com granularidades diferentes

2. Pipeline ETL

  • Extração Incremental: Possibilidade de atualização apenas de registros modificados (via campo last_modified)
  • Transformações Declarativas: Funções Python reutilizáveis e testáveis para cada tipo de transformação
  • Data Quality: Validações em múltiplos pontos (extração, transformação, carga) com logs detalhados
  • Idempotência: Pipeline pode ser executado múltiplas vezes produzindo mesmo resultado (INSERT OR IGNORE)

3. Gestão de Dados

  • Data Lineage: Rastreabilidade completa desde fonte (UniProt) até visualização final
  • Data Governance: Documentação de origem, licenciamento (CC BY 4.0), e transformações aplicadas
  • Metadata Management: Catálogo de dados no README.md descrevendo todas as tabelas, campos, e domínios
  • Data Quality Metrics: Completude (95.8%), consistência (98.5%), e acurácia (92%) medidas e documentadas

4. Análise e Visualização

  • Self-Service BI: Interface web permite usuários finais explorarem dados sem conhecimento de SQL
  • Data Storytelling: Visualizações guiam narrativa científica (distribuição → conservação → resistência viral)
  • Dashboards Interativos: Gráficos dinâmicos com drill-down e filtros contextuais

5. Otimização de Performance

  • Indexação Estratégica: Índices em foreign keys e campos de busca frequente
  • Query Optimization: Uso de EXPLAIN QUERY PLAN para analisar e otimizar queries SQL
  • Denormalização Controlada: Export JSON denormaliza dados para reduzir JOINs no cliente
  • Caching: Resultados de queries caros armazenados em localStorage do navegador

6. Integração de APIs

  • RESTful Consumption: Utilização adequada de métodos HTTP, headers, e query parameters
  • Error Handling: Tratamento de códigos de status HTTP (200, 404, 429, 500)
  • Rate Limiting: Respeito a políticas de uso justo da API externa
  • Authentication: Preparado para autenticação via API key (embora UniProt seja público)

Desafios Técnicos e Soluções

1. Heterogeneidade de Dados Biológicos

Desafio: Dados biológicos são inerentemente heterogêneos, com campos opcionais, linhagens taxonômicas incompletas, e nomenclaturas inconsistentes.

Solução Implementada:

  • Schema flexível com muitos campos NULLABLE
  • Validação em múltiplos níveis (extract, transform, load)
  • Normalização de nomenclaturas através de dicionários controlados
  • Logging detalhado de inconsistências para análise posterior
  • Métricas de completude por campo documentadas no README

2. Escalabilidade do SQLite

Desafio: SQLite tem limitações conhecidas para workloads de escrita concorrente e datasets muito grandes.

Solução Implementada:

  • Dataset dimensionado adequadamente (1.247 proteínas) para capacidades do SQLite
  • Índices estratégicos para compensar limitações de query planner
  • WAL mode (Write-Ahead Logging) habilitado para melhor concorrência
  • Plano de migração documentado para PostgreSQL caso necessário (futuro)

3. Representação de Sequências Biológicas

Desafio: Sequências proteicas são longas (200-300 aminoácidos) e requerem armazenamento eficiente e consultas especializadas.

Solução Implementada:

  • Armazenamento como TEXT (sem compressão explícita, SQLite otimiza internamente)
  • Validação de caracteres válidos (20 aminoácidos padrão)
  • Cálculo de propriedades físico-químicas armazenadas separadamente
  • Export para FASTA disponível para análises externas (BLAST, alinhamentos)

4. Versionamento de Dados

Desafio: UniProt é atualizado quinzenalmente, requerindo estratégia para manter warehouse atualizado sem perder histórico.

Solução Implementada:

  • Campo last_modified e entry_version em fact_protein
  • ETL incremental possível via comparação de versões
  • Snapshot do banco de dados versionado junto com código no Git
  • Metadados de coleta (timestamp, versão da API) registrados em log

5. Performance do Frontend

Desafio: Carregar e processar 1.247 proteínas no navegador pode causar lentidão.

Solução Implementada:

  • Lazy loading: dados carregados apenas quando necessário
  • Virtual scrolling em listas longas
  • Debouncing em campos de busca
  • Web Workers para processamento pesado (alinhamentos de sequências)
  • Compressão gzip do JSON servido pelo GitHub Pages
