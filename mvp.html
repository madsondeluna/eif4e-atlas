MVP de Engenharia de Dados

Data Warehouse para Análise Proteômica e Genômica de eIF4E em Plantas

Contexto Acadêmico

Este projeto constitui o MVP (Minimum Viable Product) desenvolvido como requisito avaliativo da disciplina de Engenharia de Dados (código 40530010057_20250_02), integrante do curso de Especialização em Data Science and Analytics da Pontifícia Universidade Católica do Rio de Janeiro (PUC-Rio).

Objetivo do MVP

O objetivo principal deste MVP é demonstrar a implementação completa de uma arquitetura de Data Warehouse aplicada a um domínio científico real, integrando conceitos fundamentais de engenharia de dados com necessidades práticas da bioinformática e genômica vegetal.

Justificativa Técnica e Científica

A escolha de proteínas eIF4E de plantas como caso de uso se justifica por múltiplos fatores:

  • Relevância Biológica: eIF4E é um fator essencial para tradução proteica e desempenha papel crucial na resistência viral em plantas cultivadas
  • Complexidade de Dados: Integra múltiplas dimensões de informação (sequências, taxonomia, funções, estruturas, variantes)
  • Dados Heterogêneos: Requer tratamento de dados estruturados (metadados) e semi-estruturados (sequências, anotações)
  • Volume Adequado: Aproximadamente 1.247 proteínas de 450 espécies, permitindo análises estatísticas significativas sem exigir infraestrutura de Big Data
  • Aplicabilidade Prática: Resultados podem ser utilizados em melhoramento genético e desenvolvimento de cultivares resistentes a vírus

Arquitetura do Data Warehouse

Implementação completa seguindo padrões de mercado e boas práticas de engenharia de dados

Visão Geral da Arquitetura

O projeto implementa uma arquitetura em três camadas (Three-Tier Architecture) composta por:

1

Camada de Apresentação

Frontend Web Client

  • HTML5: Estrutura semântica das páginas
  • CSS3: Estilização responsiva e moderna
  • JavaScript ES6+: Lógica de aplicação
  • Chart.js + D3.js: Visualizações de dados
  • JSON Export: Comunicação com camada de dados
2

Camada de Lógica

ETL Pipeline - Python

  • Extract: API REST UniProtKB com paginação
  • Transform: Normalização e validação de dados
  • Load: Inserção no warehouse SQLite
  • Rate Limiting: Respeito às políticas da API
  • Error Handling: Retry logic e logging
3

Camada de Dados

Data Warehouse - SQLite

  • Star Schema: 4 dimensões + 3 fatos
  • Dimensões: organism, gene, function, location
  • Fatos: protein, variant, domain
  • Associações: 2 tabelas many-to-many
  • Total: 9 tabelas com integridade referencial

Componentes Detalhados do Sistema

D

1. Camada de Dados

Tabelas Dimensão

  • dim_organism: Taxonomia completa (espécie, família, ordem, classe, reino)
  • dim_gene: Informações gênicas e sinônimos
  • dim_function: Anotações Gene Ontology (GO terms)
  • dim_location: Localização subcelular

Tabelas Fato

  • fact_protein: Dados centrais (sequência, peso molecular, pI)
  • fact_variant: Mutações e significância clínica
  • fact_domain: Domínios proteicos conservados
E

2. Pipeline ETL

Extract (Extração)

  • Fonte: UniProtKB REST API
  • Query: eIF4E + Viridiplantae
  • Paginação: 500 registros por página
  • Rate Limiting: 1 req/segundo

Transform

  • Normalização: Sequências e taxonomia
  • Parsing: GO terms e linhagens
  • Cálculo: Propriedades físico-químicas
  • Validação: Integridade e tipos

Load

  • Transações: BEGIN/COMMIT/ROLLBACK
  • Ordem: Dimensões → Fatos → Associações
  • Logging: Auditoria completa

Conceitos de Engenharia de Dados Aplicados

Mapeamento entre teoria e prática demonstrada no projeto

1. Modelagem de Data Warehouse

  • Star Schema: Modelo dimensional com tabela fato central (fact_protein) conectada a 4 dimensões
  • Granularidade: Nível de proteína individual permite análises detalhadas sem agregação prematura
  • Slowly Changing Dimensions: Dimensão organism implementa Type 1 (overwrite) para correções taxonômicas
  • Tabelas Fato Múltiplas: fact_variant e fact_domain complementam fact_protein com granularidades diferentes

2. Pipeline ETL

  • Extração Incremental: Possibilidade de atualização apenas de registros modificados via campo last_modified
  • Transformações Declarativas: Funções Python reutilizáveis e testáveis para cada tipo de transformação
  • Data Quality: Validações em múltiplos pontos (extração, transformação, carga) com logs detalhados
  • Idempotência: Pipeline pode ser executado múltiplas vezes produzindo mesmo resultado (INSERT OR IGNORE)

3. Gestão de Dados

  • Data Lineage: Rastreabilidade completa desde fonte (UniProt) até visualização final
  • Data Governance: Documentação de origem, licenciamento (CC BY 4.0), e transformações aplicadas
  • Metadata Management: Catálogo de dados no README.md descrevendo todas as tabelas, campos, e domínios
  • Data Quality Metrics: Completude (95.8%), consistência (98.5%), e acurácia (92%) medidas e documentadas

4. Análise e Visualização

  • Self-Service BI: Interface web permite usuários finais explorarem dados sem conhecimento de SQL
  • Data Storytelling: Visualizações guiam narrativa científica (distribuição → conservação → resistência viral)
  • Dashboards Interativos: Gráficos dinâmicos com drill-down e filtros contextuais

5. Otimização de Performance

  • Indexação Estratégica: Índices em foreign keys e campos de busca frequente
  • Query Optimization: Uso de EXPLAIN QUERY PLAN para analisar e otimizar queries SQL
  • Denormalização Controlada: Export JSON denormaliza dados para reduzir JOINs no cliente
  • Caching: Resultados de queries caros armazenados em localStorage do navegador

6. Integração de APIs

  • RESTful Consumption: Utilização adequada de métodos HTTP, headers, e query parameters
  • Error Handling: Tratamento de códigos de status HTTP (200, 404, 429, 500)
  • Rate Limiting: Respeito a políticas de uso justo da API externa
  • Authentication: Preparado para autenticação via API key (embora UniProt seja público)

Desafios Técnicos e Soluções

1

Heterogeneidade de Dados

Desafio: Dados biológicos com campos opcionais, linhagens incompletas e nomenclaturas inconsistentes.

Soluções:

  • Schema flexível com campos NULLABLE
  • Validação em múltiplos níveis do pipeline
  • Normalização via dicionários controlados
  • Logging detalhado de inconsistências
  • Métricas de completude documentadas
2

Escalabilidade do SQLite

Desafio: Limitações conhecidas para escrita concorrente e datasets muito grandes.

Soluções:

  • Dataset dimensionado adequadamente (1.247 proteínas)
  • Índices estratégicos para otimizar queries
  • WAL mode (Write-Ahead Logging) habilitado
  • Plano de migração para PostgreSQL documentado
3

Sequências Biológicas

Desafio: Sequências longas (200-300 aminoácidos) requerem armazenamento eficiente.

Soluções:

  • Armazenamento como TEXT (SQLite otimiza internamente)
  • Validação de caracteres válidos
  • Propriedades físico-químicas calculadas separadamente
  • Export para FASTA disponível
4

Versionamento de Dados

Desafio: UniProt atualizado quinzenalmente, necessário manter histórico.

Soluções:

  • Campos last_modified e entry_version em fact_protein
  • ETL incremental via comparação de versões
  • Snapshot do banco versionado no Git
  • Metadados de coleta registrados em log
5

Performance do Frontend

Desafio: Processar 1.247 proteínas no navegador pode causar lentidão.

Soluções:

  • Lazy loading de dados sob demanda
  • Virtual scrolling em listas longas
  • Debouncing em campos de busca
  • Web Workers para processamento pesado
  • Compressão gzip do JSON
